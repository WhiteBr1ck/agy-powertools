# Account switch consistency (#95, #97)

An email from the UI and an email label in a credential are independent observations. Neither proves who owns an opaque token. An account backup requires matching identities, and native Windows rejects a refresh-token fingerprint already associated with another account. A hash identifies a version or a duplicate; it is not an authentication check. Never repair a credential by changing its label.

On native Windows a switch leaves the active credential alone while the application is running. A pending intent names the target slot, expected email, blob fingerprint, canonical profile directory and a unique switch ID. The detached worker checks that the intent is still current and waits for a successful process listing with no known GUI, language-server or CLI writers before restoring. It only observes language-server/CLI processes; an unrelated instance can conservatively block a switch. The vault checks the owner and fingerprint of the bytes it actually copies. The worker clears `credential-user-scope` in the pinned profile and starts the new GUI with that same profile, even when Explorer has a different environment. A missing or inconsistent profile blocks the restore. A blocked worker does not fall back to an in-place restore.

The worker-ready acknowledgement confirms scheduling, not a successful login. While the switch is pending, stale events cannot confirm credentials or record quota. If the next session reports a different login after restore, preserve both backups, quarantine the requested slot, and ask for a fresh sign-in. An explicit login must supply new, independently matching metadata to replace a quarantined slot. The plugin cannot identify every previously mixed token, exclude an unknown writer or prevent a separately launched process from appearing after the last check. Credential restore and scope-file removal are not a single OS transaction: if scope cleanup fails after restore, startup stops and may require user intervention.
